# NyashBoard — контекст проекта

Файл для Claude Code: читается автоматически при старте сессии в этом репозитории.
Здесь то, что не видно из кода, — принятые решения, их причины и грабли, на которые
уже наступали.

## О чём проект

Социальная платформа: лента, анонимный общий чат, анонимные каналы с несколькими
управляющими, друзья и личные чаты. Ванильный JavaScript без сборки и фреймворков,
Firebase для данных и входа, публикация на GitHub Pages.

Главная идея, из которой растёт почти вся архитектура: **анонимность должна быть
настоящей, а не нарисованной**. Если что-то «скрыто», оно должно быть недоступно на
уровне правил базы, а не просто не отрисовано на экране.

## Как общаться с автором

- Автор проекта — Неко. Обращение — на «ты».
- Ценит прямоту: если решение плохое или невозможное — сказать об этом сразу, а не
  делать вид, что всё получится. Он сам отлично ловит недомолвки.
- Ценит объяснение причин, а не только фактов. «Не работает» бесполезно, «не работает,
  потому что правило Firestore не пускает» — то, что нужно.
- Не любит, когда ограничения замалчивают. Все компромиссы проговариваются явно и
  попадают в раздел ограничений README.
- Пишет с телефона, публикует через Termux. Учитывать это в предложениях.

## Технические ограничения, из которых всё выросло

- **Всё должно быть бесплатным.** Никаких Cloud Functions, никакого тарифа Blaze.
  Firebase Storage не используется: с конца 2024 Google требует привязанный биллинг
  даже для создания хранилища. Картинки идут в цепочку ImgBB → Catbox → Uguu.
- **Экономия обращений к базе.** Бесплатный лимит чтений тратится быстро, поэтому:
  ответы под записями грузятся лениво по мере прокрутки; списки ограничены лимитами;
  личные данные пишутся пачками с задержкой, а не на каждое действие.
- **Никаких составных индексов.** Запросы вида «фильтр по одному полю + сортировка по
  другому» требуют индекса, который Firestore не создаёт сам. Везде используется
  фильтрация запросом и сортировка на клиенте. Если добавляешь запрос — проверь это.

## Ключевые архитектурные решения

### Владение контентом работает и для гостей
У каждого посетителя есть анонимная сессия Firebase со своим идентификатором. При
создании записи рядом пишется документ-секрет (`postSecrets`, `replySecrets`,
`chatMessageSecrets`), который **никто не может прочитать** — он существует только
для проверок в правилах при изменении и удалении. Интерфейс ориентируется на локальный
список своих идентификаторов (`ownership.js`), потому что сам секрет недоступен даже
своему клиенту.

Известное следствие: если анонимная сессия сменилась (автоочистка в Firebase или
очистка данных браузера), владение старым контентом теряется. Это ожидаемо.

### NUID хранится отдельно от профиля
Документ `users/{uid}` читается публично целиком, поэтому идентификатор в нём означал
бы, что «скрытие» — фикция. NUID лежит в `userNuids/{uid}`, правило сверяется с
настройкой владельца. Плюс обратный индекс `nuidIndex/{NUID}`, где **разрешён `get`,
но запрещён `list`**: зная идентификатор, человека найдёшь, а собрать чужие — нет.

### Приватные данные привязаны к аккаунту, но недоступны никому
Интересы, отметки «прочитано», подписки и друзья лежат в подколлекциях пользователя с
доступом только для владельца. Именно на сервере, а не в браузере: иначе при заходе с
другого устройства аккаунт терял бы смысл. Механика в `synced-store.js`.

### Друзья и проверка взаимности
Список друзей читается только владельцем. Но правила **могут** проверить наличие
записи, не раскрывая список, — на этом работает выдача NUID друзьям. Для взаимности
разрешено точечное чтение одного документа: своей записи в чужом списке.

### Рекомендации
Прозрачная система очков в `ranking.js`, без чёрного ящика. Профиль интересов —
три словаря (слова, хештеги, авторы), наполняется лайками. Всё считается на клиенте
по уже загруженным записям, дополнительных запросов нет.

## Правила работы с кодом

- **Комментарии объясняют «почему», а не «что».** Особенно там, где решение выглядит
  странным: почему сортировка на клиенте, почему секрет недоступен, почему порядок
  шрифтов именно такой.
- **Тексты интерфейса склоняются по роду** через `gendered()` из `ui.js`. Не писать
  «пиши первой» напрямую.
- **Иконки интерфейса** — глифы Nerd Font с классом `.nf`. Эмодзи-шрифт не должен их
  перебивать, поэтому Monaspace всегда первым в списке `font-family`.
- **Стандартные аватарки и иконка вкладки** генерируются кодом под цвет темы
  (`default-avatar.js`, `favicon.js`). Не возвращать статичные картинки.

## Проверки перед сборкой

Обязательно прогонять, это ловило реальные поломки:

```bash
# синтаксис всех модулей
for f in js/*.js; do node --input-type=module --check < "$f" || echo "FAIL $f"; done

# всё остальное — одной командой
python3 tools/check.py
```

`tools/check.py` проверяет: импорт того, чего модуль не экспортирует; **вызов
чужой функции без импорта**; циклические зависимости; баланс скобок в
`firestore.rules` и `style.css`; наличие в разметке всех `id`, которые ищет JS.
Возвращает код 1 при находках, так что годится и для CI.

Про `id`: навигация собирается из `layout.js`, поэтому `profileIcon` и
`profilePic` в HTML отсутствуют намеренно — скрипт знает про шаблоны в JS и
такие случаи не считает ошибкой.

## Грабли, на которые уже наступали

- `position: relative` в общем правиле затирал `sticky` у шапки — она уезжала при
  прокрутке.
- Noto Color Emoji в Google Fonts отдаётся с диапазоном, включающим цифры (для
  эмодзи-клавиш). Если поставить его первым в `font-family`, все цифры сайта
  начинают рисоваться им.
- Ошибка внутри обработчика `onAuthStateChanged` роняла весь вход: аккаунт в базе
  создавался, а интерфейс оставался «не вошедшим». Всё, что там может упасть, должно
  быть в `try/catch`.
- Тема применялась после загрузки модулей и страница мигала. Теперь атрибуты ставит
  маленький скрипт в `<head>` до первой отрисовки.
- Загрузка всех ответов сразу давала 50 запросов к базе при открытии ленты.
- `data.js` звал `generateUniqueNuid`, `registerNuid` и `migrateLegacyNuid`,
  не импортировав их: создание аккаунта падало с `ReferenceError`, а `try/catch`
  во входе делал поломку тихой — человек входил, а профиля в базе не появлялось.
  Причиной был страх цикла `data → nuid → auth → data`; цикл разорван тем, что
  `nuid.js` больше не зависит от `auth.js` и принимает uid параметром.
- `orderBy("createdAt", "asc")` вместе с `limit()` отдаёт САМЫЕ СТАРЫЕ записи,
  а не свежие. Из-за этого чат замирал после сотого сообщения. Везде, где есть
  лимит, сортировка должна быть `desc`, а разворот — на клиенте.
- `onAuthChange` срабатывает с `null` не только при выходе, но и у гостя на
  каждой загрузке страницы (гость — это анонимная сессия, `currentUser === null`).
  Кэши, которые чистились по этому событию, стирали гостю подписки, интересы и
  прочитанное при каждом переходе. Для «аккаунт ушёл» есть отдельный
  `onAccountLeave` из `auth.js`.
- `linkifyMentions()` работает по уже экранированному тексту, поэтому
  `escapeHtml` не должен оставлять там решёток: с `&#39;` апостроф превращался
  в хештег `#39`. Апостроф экранируется как `&apos;`.
- `onSnapshot` присылает снимок на каждое изменение любой записи, включая чужой
  лайк. Полная перерисовка ленты на каждый снимок меняла порядок под пальцами и
  заново тянула превью ответов. Порядок фиксируется один раз, лайки правятся
  в уже нарисованной карточке.
- `URL.createObjectURL()` в шаблоне строки — новая ссылка на каждую перерисовку
  и ни одной освобождённой. Ссылку делать один раз и отзывать при удалении.

## Публикация

Изменения в правилах **обязательно** доезжают до Firebase, иначе всё падает с
`Missing or insufficient permissions`. Для этого есть workflow
`.github/workflows/deploy-rules.yml` — деплоит правила сам при пуше. Требует секретов
`FIREBASE_SERVICE_ACCOUNT` и `FIREBASE_PROJECT_ID`.

`js/config.js` содержит ключи и **не должен затираться** при обновлении — `deploy.sh`
это учитывает.
